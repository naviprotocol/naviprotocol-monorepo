title: Deposit

The deposit builder appends vault deposit calls to a transaction you provide. It dispatches to the NAVI or Volo implementation automatically based on `vault.source`, so the same call works for both.

## Core Features

- **Unified Interface**: One builder for both NAVI and Volo vaults
- **Automatic Receipt Handling**: Reuses an existing receipt when the owner has one, creates one otherwise
- **Flexible Coin Sourcing**: Split from the owner's balance, from the gas coin, or supply your own coin
- **Slippage Protection**: Enforce a minimum share floor on Volo vaults

`client` is optional — it defaults to the public mainnet fullnode; pass your own for a private endpoint.

## API Reference

### depositPTB

Build a deposit into a vault. See [documentation](/typedoc/functions/_naviprotocol_vault.depositPTB.html) for details.

**Usage Example**

```typescript
import { depositPTB } from '@naviprotocol/vault'
import { Transaction } from '@mysten/sui/transactions'

const tx = new Transaction()

// Deposit 1.5 tokens — amount is a human-readable decimal string
const result = await depositPTB(tx, vault, owner, '1.5')

// Deposit SUI, splitting from the gas coin
const suiResult = await depositPTB(tx, suiVault, owner, '1.5', {
  useGasCoin: true // Optional: split from the gas coin
})

// Deposit from a coin you already hold in the PTB
const coinResult = await depositPTB(tx, vault, owner, '1.5', {
  coin: myCoin // Optional: supply your own coin object
})

// Volo only: require a minimum share floor
const protectedResult = await depositPTB(tx, voloVault, owner, '1.5', {
  expectedShares: 1_400_000_000n // Optional: on-chain minimum-shares assert
})
```

**Parameters**

- `tx`: The transaction to append calls to
- `vaultIdentifier`: A vault id or an already-fetched vault object
- `owner`: Sui address the deposit is credited to. Existing receipts are reused when present
- `amount`: **Human-readable decimal string** in vault coin units, e.g. `'1.5'` or `'0.0002'`
- `options.coin`: Coin object to deposit from. When omitted, one is split for `amount`
- `options.useGasCoin`: Split from the gas coin instead of a coin object lookup. Ignored when `coin` is given
- `options.client`: gRPC client for on-chain reads
- `options.expectedShares`: Minimum shares the deposit must mint. **Volo only** — see below

## Consuming the Result

This is the step most easily missed. The deposit returns objects that Sui requires you to consume, and the transaction will fail if you leave them dangling. The shape differs by source:

| Source | Return shape                    | Must consume                |
| ------ | ------------------------------- | --------------------------- |
| NAVI   | `[Receipt, shares]`             | `result[0]` — the receipt   |
| Volo   | `[request_id, Receipt, change]` | `result[1]` and `result[2]` |

```typescript
import { depositPTB } from '@naviprotocol/vault'
import { Transaction } from '@mysten/sui/transactions'

const tx = new Transaction()
const result = await depositPTB(tx, vault, owner, '1.5', { client })

if (vault.source === 'navi') {
  // NAVI returns (Receipt, shares)
  tx.transferObjects([result[0]], owner)
} else {
  // Volo returns (request_id, Receipt, change)
  tx.transferObjects([result[1], result[2]], owner)
}
```

<Callout type="warn">
  Always branch on `vault.source`, never on `vault.protocol`. An `astros`-protocol vault is served
  through either source, so branching on `protocol` will index the wrong tuple slot.
</Callout>

## Amount Units

`depositPTB` takes a **human-readable decimal string**, parsed against `vault.assets.baseCoin.decimals`. It does not take a number, and it does not take raw base units.

```typescript
await depositPTB(tx, vault, owner, '1.5') // 1.5 tokens
await depositPTB(tx, vault, owner, '0.0002') // 0.0002 tokens
```

The string must be a valid decimal, strictly positive, and carry no more fractional digits than the coin supports. Anything else throws `INVALID_AMOUNT`:

```typescript
await depositPTB(tx, vault, owner, '0') // throws: must be greater than zero
await depositPTB(tx, vault, owner, '-1') // throws: must be greater than zero
await depositPTB(tx, vault, owner, 'abc') // throws: not a decimal string
await depositPTB(tx, vault, owner, '0.0000000001') // throws on a 9-decimal coin
```

If you already hold raw base units as a `bigint`, use the [protocol namespaces](/vault/protocols) instead of stringifying by hand — `navi.depositPTB` and `volo.depositPTB` take `bigint` directly.

## Slippage Protection

Volo deposits settle asynchronously at whatever rate an operator executes them at. `expectedShares` sets a floor the contract enforces at execution time, aborting the request if it would mint fewer shares:

```typescript
import { depositPTB, getVault } from '@naviprotocol/vault'

const vault = await getVault(vaultId)

if (vault.source === 'volo' && vault.totalShares && vault.totalStaked) {
  // shares = amount * totalShares / totalStaked, both sides in the same units,
  // so the coin's decimals cancel out and do not appear here.
  const estimated = (1.5 * Number(vault.totalShares)) / vault.totalStaked

  // Allow 1% slippage against that estimate
  const floor = BigInt(Math.floor(estimated * 0.99))

  await depositPTB(tx, vault, owner, '1.5', { expectedShares: floor })
}
```

<Callout>
  `totalShares` can exceed `Number.MAX_SAFE_INTEGER`, so `Number()` loses precision on large vaults.
  That is acceptable for a slippage floor you are rounding down anyway, but do not reuse this
  pattern where exactness matters — keep the value as a `bigint` instead.
</Callout>

<Callout type="warn">
  `expectedShares` is currently **ignored** for NAVI vaults rather than rejected. NAVI deposits have
  no slippage parameter, so passing a non-zero floor there silently provides no protection. Guard on
  `vault.source === 'volo'` as shown above.
</Callout>

## What the Builder Does For You

Both implementations do meaningful setup work before the deposit call, so you do not have to:

**NAVI**

1. Syncs the vault's cached balance in every registered lending market
2. Harvests active market reward rules so indices are current
3. Reuses the owner's lowest-share receipt, or creates a new one
4. Deposits into the vault's default lending pool

**Volo**

1. Reuses the owner's lowest-share receipt, or lets the contract mint one
2. Creates a deposit request with your `expectedShares` floor
3. Records the request off-chain so it appears in [`getPendingRequests`](/vault/pending-requests)

## Errors

| Code                   | Cause                                                           |
| ---------------------- | --------------------------------------------------------------- |
| `INVALID_AMOUNT`       | `amount` is not a positive decimal within the coin's precision  |
| `VAULT_NOT_FOUND`      | No vault matches the given id                                   |
| `VAULT_UNSUPPORTED`    | The vault's source has no deposit builder                       |
| `VAULT_CONFIG_INVALID` | The vault's default pool or market could not be resolved (NAVI) |

See [Error Handling](/vault/errors) for how to branch on these.
