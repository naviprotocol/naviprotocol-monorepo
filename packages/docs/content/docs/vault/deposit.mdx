title: Deposit & Withdraw
---

Both builders append vault calls to a transaction you provide and dispatch to the NAVI or Volo implementation automatically based on `vault.source`, so the same call works for both. Neither signs or executes anything.

Full signatures are in the API reference: [`depositPTB`](/typedoc/functions/_naviprotocol_vault.depositPTB.html), [`withdrawPTB`](/typedoc/functions/_naviprotocol_vault.withdrawPTB.html).

## Deposit

```typescript
import { depositPTB } from '@naviprotocol/vault'
import { Transaction } from '@mysten/sui/transactions'

const tx = new Transaction()

// Amount is a human-readable decimal string in vault coin units
const result = await depositPTB(tx, vault, owner, '1.5')

// Split from the gas coin instead of looking up a coin object
await depositPTB(tx, suiVault, owner, '1.5', { useGasCoin: true })

// Supply your own coin
await depositPTB(tx, vault, owner, '1.5', { coin: myCoin })

// Volo only: require a minimum share floor
await depositPTB(tx, voloVault, owner, '1.5', { expectedShares: 1_400_000_000n })
```

### Amount Units

String amounts are parsed against `vault.assets.baseCoin.decimals`. The string must be a valid decimal, strictly positive, and carry no more fractional digits than the coin supports. Anything else throws `INVALID_AMOUNT`:

```typescript
await depositPTB(tx, vault, owner, '0') // throws: must be greater than zero
await depositPTB(tx, vault, owner, '-1') // throws: must be greater than zero
await depositPTB(tx, vault, owner, 'abc') // throws: not a decimal string
await depositPTB(tx, vault, owner, '0.0000000001') // throws on a 9-decimal coin
```

For PTB composition, `amount` can instead be a `TransactionArgument` or `TransactionResult` holding raw base units. In that form you must also pass the matching `options.coin` — the SDK cannot create a coin from a dynamic amount:

```typescript
const amount = tx.pure.u64(1_500_000_000n)
const [coin] = tx.splitCoins(tx.gas, [amount])
await depositPTB(tx, suiVault, owner, amount, { coin })
```

The top-level builder does not accept a literal `bigint`. Use the [protocol namespaces](/vault/protocols) when you already hold a raw amount — `navi.depositPTB` and `volo.depositPTB` take `bigint` directly.

### Consuming the Result

The builder normalizes the protocol-specific tuples into one object and transfers owned return values to `owner` automatically:

| Source | Return shape             | Automatic transfer                |
| ------ | ------------------------ | --------------------------------- |
| NAVI   | `{ receipt, shares }`    | `receipt` to `owner`              |
| Volo   | `{ receipt, requestId }` | `receipt` and `charge` to `owner` |

<Callout type="warn">
  Do not transfer `result.receipt` again. The top-level builder has already consumed that handle by
  transferring it to `owner`. Raw `navi.depositPTB` and `volo.depositPTB` calls still return
  unconsumed tuples; see [Protocol Namespaces](/vault/protocols).
</Callout>

### Slippage Protection

Volo deposits settle asynchronously at whatever rate an operator executes them at. `expectedShares` sets a floor the contract enforces at execution time, aborting the request if it would mint fewer shares:

```typescript
import { depositPTB, getVault } from '@naviprotocol/vault'

const vault = await getVault(vaultId)

if (vault.source === 'volo' && vault.totalShares && vault.totalStaked) {
  // shares = amount * totalShares / totalStaked, both sides in the same units,
  // so the coin's decimals cancel out and do not appear here.
  const estimated = (1.5 * Number(vault.totalShares)) / vault.totalStaked
  const floor = BigInt(Math.floor(estimated * 0.99)) // allow 1% slippage

  await depositPTB(tx, vault, owner, '1.5', { expectedShares: floor })
}
```

<Callout>
  `totalShares` can exceed `Number.MAX_SAFE_INTEGER`, so `Number()` loses precision on large vaults.
  That is acceptable for a slippage floor you are rounding down anyway, but do not reuse this
  pattern where exactness matters — keep the value as a `bigint` instead.
</Callout>

## Withdraw

```typescript
import { withdrawPTB } from '@naviprotocol/vault'

type WithdrawTarget =
  | { kind: 'amount'; amount: string } // human-readable decimal string
  | { kind: 'shares'; shares: string | bigint } // raw on-chain share count
  | { kind: 'all' } // everything currently available

await withdrawPTB(tx, vault, owner, { kind: 'amount', amount: '1.5' })
await withdrawPTB(tx, vault, owner, { kind: 'shares', shares: '1000000' })
await withdrawPTB(tx, vault, owner, { kind: 'all' })
```

<Callout>
  For Volo, `{ kind: 'all' }` covers only the receipts eligible **right now**. Receipts still inside
  the withdraw lock, or already carrying a pending withdraw request, are skipped — so "all" can
  withdraw less than the wallet's total shares. Check
  [`getPendingRequests`](/vault/pending-requests) if the result looks short.
</Callout>

### Consuming the Result

The return type differs by source, and this is the single most important difference between the two:

| Source | Returns                                     | Settlement                            |
| ------ | ------------------------------------------- | ------------------------------------- |
| NAVI   | `TransactionResult` — the withdrawn coin    | Immediate, same transaction           |
| Volo   | `TransactionResult[]` — created request ids | Asynchronous, executed by an operator |

```typescript
import { Transaction, TransactionResult } from '@mysten/sui/transactions'

if (vault.source === 'navi') {
  // A coin you must consume
  const coin = (await withdrawPTB(tx, vault, owner, {
    kind: 'amount',
    amount: '1.5'
  })) as TransactionResult
  tx.transferObjects([coin], owner)
} else {
  // Request ids — droppable u64s, nothing to consume. The principal arrives
  // later, when an operator executes the request.
  await withdrawPTB(tx, vault, owner, { kind: 'shares', shares: '1000000' })
}
```

<Callout type="warn">
  A NAVI withdrawal hands you a coin that Sui requires you to consume — transfer it, or the
  transaction will fail. A Volo withdrawal returns nothing you need to consume, and moves no
  principal in this transaction.
</Callout>

### Receipt Planning

A wallet can hold several receipts for one vault. Both implementations consume them **smallest-first**, which retires dust receipts before touching a large one. A single `withdrawPTB` may therefore append several on-chain calls: NAVI merges the resulting coins so you always get exactly one coin back, while Volo creates one request per receipt drawn from.

If the owner's receipts cannot cover the request, the builder throws `INSUFFICIENT_BALANCE` rather than withdrawing less than you asked for:

```typescript
import { withdrawPTB, isVaultSdkError } from '@naviprotocol/vault'

try {
  await withdrawPTB(tx, vault, owner, { kind: 'amount', amount: '1000' }, { client })
} catch (error) {
  if (isVaultSdkError(error) && error.code === 'INSUFFICIENT_BALANCE') {
    console.log(error.details?.uncoveredShares) // or uncoveredAmount for NAVI
    console.log(error.details?.excludedReceipts) // Volo: [{ id, reason }]
  }
}
```

The Volo contract rejects a withdrawal on a receipt that already has a pending withdraw request, or one still inside its withdraw lock — locked for `locking_time_for_withdraw` after its last _executed_ deposit. The SDK excludes both up front and lists them in `details.excludedReceipts`.

### Unit Conversion Caveats

The two protocols burn different things on-chain, and the SDK converts for you:

- **NAVI** withdraws by **asset amount**. A `shares` target is converted at the vault's current on-chain exchange rate before planning.
- **Volo** burns **shares**. An `amount` target is converted from the API's `totalStaked`/`totalShares` snapshot.

<Callout>
  For Volo, that conversion is an **estimate**. The request settles at whatever rate the operator
  executes it at, which may differ from the snapshot the SDK converted against. Use
  `{ kind: 'shares' }` when you need an exact share count burned.
</Callout>

## What the Builders Do For You

Both implementations do setup work before the main call, so you do not have to. **NAVI** syncs the vault's cached balance in every registered lending market, harvests active reward rules so indices are current, reuses the owner's lowest-share receipt or creates one, deposits into the vault's default lending pool, and transfers the receipt to `owner`.

**Volo** reuses the owner's lowest-share **eligible** receipt — one whose status accepts a new request — or passes `option::none` and lets the contract mint one, creates the request with your `expectedShares` floor, records it off-chain so it appears in [`getPendingRequests`](/vault/pending-requests), and transfers the receipt and charge coin to `owner`.

## Errors

| Code                   | Cause                                                                             |
| ---------------------- | --------------------------------------------------------------------------------- |
| `INVALID_AMOUNT`       | An amount is invalid, or a PTB amount was passed without `options.coin`           |
| `INSUFFICIENT_BALANCE` | The owner's receipts cannot cover the withdrawal                                  |
| `VAULT_NOT_FOUND`      | No vault matches the given id                                                     |
| `VAULT_UNSUPPORTED`    | The vault's source has no builder for this operation                              |
| `VAULT_CONFIG_INVALID` | A NAVI default pool could not be resolved, or a Volo `amount` could not be priced |

See [Error Handling](/vault/errors) for how to branch on these.
