---
title: Error Handling
---

Every failure the Vault SDK raises is a `VaultSdkError` carrying a stable, machine-readable `code`. Branch on `code` rather than parsing messages — messages are free-form and may change between releases.

## Core Features

- **Stable Codes**: A fixed set of codes safe to switch on
- **Structured Details**: Machine-readable context attached to each error
- **Cause Chaining**: The underlying error preserved as `cause`
- **Type Guard**: `isVaultSdkError` for narrowing a caught `unknown`

## Basic Usage

```typescript
import { getVault, isVaultSdkError } from '@naviprotocol/vault'

try {
  const vault = await getVault('0x...')
} catch (error) {
  if (isVaultSdkError(error)) {
    console.log(error.code) // 'VAULT_NOT_FOUND'
    console.log(error.message) // human-readable, not a stable contract
    console.log(error.details) // structured context
    console.log(error.cause) // underlying error, when there was one
  }
  throw error
}
```

## VaultSdkError

- `code`: Stable failure code — see the table below
- `message`: Human-readable description. **Not** part of the stable contract
- `details`: Structured context, e.g. the vault id or the offending amount
- `cause`: The underlying error this one wraps, when applicable
- `toJSON()`: Serializable form for logs — name, code, message, and details. Deliberately omits `cause` and the stack

## Error Codes

All codes are exported as `VAULT_SDK_ERROR_CODES`, with the union type `VaultSdkErrorCode`.

| Code                         | Meaning                                                                            |
| ---------------------------- | ---------------------------------------------------------------------------------- |
| `VAULT_NOT_FOUND`            | No vault matches the given id                                                      |
| `VAULT_UNSUPPORTED`          | The vault does not support this operation, e.g. a `navi.*` builder on a Volo vault |
| `VAULT_CONFIG_INVALID`       | The vault's API or on-chain configuration is missing a field the operation needs   |
| `INVALID_ARGUMENT`           | An argument other than an amount is missing or malformed                           |
| `INVALID_AMOUNT`             | An amount or share count is not a valid positive value                             |
| `INVALID_REQUEST_TYPE`       | A pending request was passed to the wrong cancel builder                           |
| `INSUFFICIENT_BALANCE`       | The owner's receipts cannot cover the requested withdrawal                         |
| `OPERATION_NOT_SUPPORTED`    | The operation is not implemented by this SDK                                       |
| `CHAIN_QUERY_FAILED`         | An on-chain read failed at the transport level                                     |
| `CHAIN_DATA_INVALID`         | On-chain data was read but has an unexpected shape                                 |
| `API_REQUEST_FAILED`         | A NAVI open API request failed — network error or non-2xx                          |
| `API_RESPONSE_INVALID`       | The API responded successfully but with an unexpected payload                      |
| `RATE_LIMITED`               | The API responded with HTTP 429. A specialization of `API_REQUEST_FAILED`          |
| `UNSUPPORTED_CONFIG_VERSION` | Reserved for a future on-chain config version this build cannot parse              |
| `UNSUPPORTED_DEPOSIT_ASSET`  | Reserved for a deposit asset the vault does not accept                             |
| `REQUEST_NOT_FOUND`          | Reserved for looking up a pending request that does not exist                      |

<Callout>
  `RATE_LIMITED` is raised **instead of** `API_REQUEST_FAILED` on HTTP 429, not in addition to it.
  Handle both if you are catching API failures generically.
</Callout>

## Branching on Codes

```typescript
import { depositPTB, isVaultSdkError, VAULT_SDK_ERROR_CODES } from '@naviprotocol/vault'

try {
  await depositPTB(tx, vault, owner, amount)
} catch (error) {
  if (!isVaultSdkError(error)) throw error

  switch (error.code) {
    case VAULT_SDK_ERROR_CODES.INVALID_AMOUNT:
      // Bad user input — surface a validation message
      break
    case VAULT_SDK_ERROR_CODES.VAULT_NOT_FOUND:
      // Stale vault id — refresh the vault list
      break
    case VAULT_SDK_ERROR_CODES.RATE_LIMITED:
      // Back off and retry
      break
    default:
      throw error
  }
}
```

## Reading Details

`details` carries operation-specific context. The most useful case is an insufficient balance, where it tells you exactly how far short the request fell:

```typescript
import { withdrawPTB, isVaultSdkError } from '@naviprotocol/vault'

try {
  await withdrawPTB(tx, vault, owner, { kind: 'amount', amount: '1000' }, { client })
} catch (error) {
  if (isVaultSdkError(error) && error.code === 'INSUFFICIENT_BALANCE') {
    // NAVI: requestedAmount, uncoveredAmount
    // Volo: requestedShares, uncoveredShares, excludedReceipts
    console.log(error.details?.uncoveredShares)

    // Volo lists why each receipt was skipped: locked, or already pending
    for (const excluded of (error.details?.excludedReceipts as { id: string; reason: string }[]) ??
      []) {
      console.log(excluded.id, excluded.reason)
    }
  }
}
```

Other common `details` keys:

- `vaultId`, `owner` — on most vault-scoped failures
- `url`, `status` — on `API_REQUEST_FAILED` and `RATE_LIMITED`
- `expected`, `actual` — on `VAULT_UNSUPPORTED` and `INVALID_REQUEST_TYPE`
- `amount`, `target` — on `INVALID_AMOUNT`

## Retry Strategy

Codes fall into three groups, and only one is worth retrying:

**Retryable** — transient, retry with backoff:

- `RATE_LIMITED` — back off before retrying
- `API_REQUEST_FAILED` — network or upstream failure
- `CHAIN_QUERY_FAILED` — RPC transport failure

**Not retryable — fix the input:**

- `INVALID_AMOUNT`, `INVALID_ARGUMENT`, `INVALID_REQUEST_TYPE`
- `VAULT_NOT_FOUND`, `VAULT_UNSUPPORTED`
- `INSUFFICIENT_BALANCE`

**Not retryable — report it:**

- `VAULT_CONFIG_INVALID`, `CHAIN_DATA_INVALID`, `API_RESPONSE_INVALID` — these indicate a data or configuration problem upstream rather than anything the caller did

```typescript
import { isVaultSdkError, type VaultSdkErrorCode } from '@naviprotocol/vault'

const RETRYABLE: VaultSdkErrorCode[] = ['RATE_LIMITED', 'API_REQUEST_FAILED', 'CHAIN_QUERY_FAILED']

async function withRetry<T>(fn: () => Promise<T>, attempts = 3): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await fn()
    } catch (error) {
      const retryable = isVaultSdkError(error) && RETRYABLE.includes(error.code)
      if (!retryable || attempt >= attempts) throw error
      await new Promise((resolve) => setTimeout(resolve, 2 ** attempt * 500))
    }
  }
}
```

## Logging

`toJSON()` gives a serializable form safe to log, omitting the stack and the non-JSON-safe `cause`:

```typescript
import { isVaultSdkError } from '@naviprotocol/vault'

try {
  await getPositions(owner)
} catch (error) {
  if (isVaultSdkError(error)) {
    logger.error('vault sdk failure', error.toJSON())
  }
  throw error
}
```
