# SDK 开仓/加杠杆 0.1% 目标容差：实现与验证

日期：2026-11-24。分支 `zado/multiply-package`，基于 HEAD `b12eb2ac2ec61213a3ee20b58e55ae372cbdeabb` 的现有本地 Astros 改动继续开发。本次未提交、推送、发布 npm 或部署；API/前端无改动。

## 实现范围

- `planner.ts` 仅 `open` 和向上 `set_leverage` 使用 `abs(actual - target) / target <= 0.001`，包含两端边界。
- 首笔候选和最终求解结果使用同一容差。返回真实估值，不把 actual 改写成 target。
- `add_principal`、减杠杆和提取本金保持 0.01%；原 NO_OP 门槛保持不变。
- HF/LTV、maxLeverage、费用、整数精度、容量和资金守恒不变。maxLeverage 继续使用独立的 0.01% 原有取整带，quote、build 和链上检查一致，不能跟随目标容差放宽。
- `amounts.ts` 只有说明注释更新；README 分别解释目标容差和 maxLeverage 上限。转换器、资金、E-Mode 和 build 源文件与本次修改前字节一致。

## 回归与复查

520 项测试通过（修改前 499 项，新增 21 项），typecheck、lint、build 和 `git diff --check` 通过。Lint 只有原有 React detect 警告。

新增覆盖：

- 正负 0.1% 精确边界接受；边界外回退；真实输出保留并能 build。
- 6/9 位资产已有仓位加杠杆一次报价；非零 flash/borrow fee 下资金守恒与 build。
- add_principal、向下 set_leverage、remove_principal 保持原精度。
- 误差在新容差内但 HF/LTV/maxLeverage 不安全的首笔候选不可接受；允许回退找到安全计划。
- 最小到账风险超过限制且无可行解时必须失败；maxLeverage 请求准入、build 上限不扩大。
- 已接受报价的 flashRepayment 被改动后，即使重算 checksum，资金校验仍拒绝。
- 原同池容量回归在四组小数位组合下继续覆盖“容量少一原子”。这些用例的转换偏差从 0.1% 改为 1%，使其继续触发旧求解器；否则新容差可能先找到另一份资金占用更低的安全计划。

复查结论：本次改动未发现新的阻断问题。对 planner 的修改前后文本复核确认只有容差选择及两处使用点变动；风险/资金/build 可执行代码未改变。

### 风险边界的预期行为

- 5.70x / minHF 1.05 的首笔候选不安全。10 万 USDC 场景在 4 次报价后找到 5.694686583670x，误差 0.093217830%，最差 HF 1.050039305774，因此现在可以合法成功；100 USDC 的同目标本次仍失败。不能保证求解器总能找到容差内的安全解。
- 5.04x / minHF 1.08 的相邻边界样本仍失败。
- 5.71x / minHF 1.05 和 5.05x / minHF 1.08，两个金额、修改前后都因 HF 不足拒绝，共 8 组反例。没有为了达到“一次报价”绕过风险校验。
